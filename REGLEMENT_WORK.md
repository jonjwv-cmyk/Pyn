# Регламент работы

Этот регламент — **основной** рабочий порядок для любых ИИ-агентов в проекте Pyn
(Grok, Claude, Cursor, Copilot, Codex и др.). Он важнее личных привычек агента и
дефолтных «развёрнутых» протоколов, но **не отменяет**:

- системные ограничения среды и безопасность;
- прямые новые указания пользователя;
- checkpoint / rollback **перед первой записью** в код;
- обязательную проверку после правок (typecheck / dev / UI — по задаче).

Главная цель: **максимальная экономия токенов, команд и чтения файлов без потери
качества результата.**

Качество = правильное понимание + минимальный diff + проверяемый результат.
Качество ≠ максимальный объём чтения, логов, отчётов или «на всякий случай».

---

## 0. Operating profile (жёстко)

### Делать

1. Сформулировать цель пользователя в **1–2 предложениях**.
2. План на **3–6 пунктов** (кратко).
3. Действовать **одним проверяемым шагом** за раз; после шага — результат.
4. Читать **только** то, без чего нельзя сделать следующий шаг.
5. Поиск: `rg` / точечный path / `head`/`tail` / limit строк. Не `find ~`, не
   обход всего monorepo.
6. Отвечать коротко: что сделано → что получилось → ещё нужно: да/нет.
7. При handoff от пользователя (commit, stash, «уже на проде») — **доверять** и
   не перепроверять заново без причины.
8. Work-state / длинные отчёты — только на milestone или в конце coding-задачи,
   компактно.

### Не делать

1. Не читать файлы, skills, PROJECT_MAP, «карту всего» без нужды для *этого* шага.
2. Не сканировать весь проект и не гонять широкий `find` по home/диску.
3. Не выводить большие логи/diff целиком — только релевантный хвост или match.
4. Не повторять секреты, cookie, ключи, большие payload.
5. Не запускать дорогие сборки, если хватает typecheck / точечного теста.
6. Не вести 2+ независимых расследования параллельно «на всякий».
7. Не перечитывать один и тот же большой файл без новой причины.
8. Не плодить новые rules/AGENTS/skills-деревья — править этот файл и тонкие
   entrypoint'ы (см. §8).
9. Не переписывать Electron/UI/preload/vite «для красоты» без воспроизведённой
   ошибки и явного разрешения.
10. Не раздувать ответ completion-эпопеей на read-only вопрос.

### Если глобальные правила агента спорят с этим регламентом

| Тема | Приоритет |
|------|-----------|
| Экономия чтения, стиль ответа, порядок шагов | **Этот регламент** |
| Checkpoint перед write, не уничтожать работу пользователя, evidence | **Safety global** (не ослаблять) |
| Scope / не трогать лишнее | Оба: минимальный diff + checkpoint |

Перед write: минимальная инспекция (`git status --short`, HEAD, что реально
меняется) + checkpoint. Не полный «session archaeology».

## 1. Старт задачи

1. Кратко сформулировать реальную цель (1–2 предложения).
2. Короткий план на 3–6 пунктов.
3. Действия — только после плана (кроме тривиального «прочитай X»).
4. Один проверяемый шаг за раз.
5. После каждого шага — проверка результата.
6. Если направление бесполезно — остановить и не возвращаться без причины.

Handoff / resume: сначала сообщение пользователя и (если есть) work-state;
не начинать анализ «с нуля», если факты уже даны.

---

## 2. Экономия контекста

Читать файлы, искать по проекту и запускать команды **можно**, только если:

- без этого нельзя сделать следующий конкретный шаг;
- есть точная ошибка, которую нужно устранить;
- пользователь явно просил проверить конкретное место;
- изменение затрагивает общий контракт, запуск, сборку или UI, и без проверки
  можно пропустить поломку.

Иначе — **не трогать**.

Дополнительно:

- batch tool-call'ов: только то, что нужно **этому** шагу (обычно 1–3), не
  «разведка всего сразу»;
- subagents / full review / design-pipeline — только если пользователь просил
  или задача без этого объективно не закрывается;
- после ошибки инструмента — один узкий retry, не веер альтернатив.

---

## 3. Если регламент мешает

Если правило мешает нормально решить задачу — **остановиться и спросить**:

- какое правило мешает;
- почему;
- что именно агент хочет сделать;
- какой риск, если не сделать исключение.

Без явного разрешения пользователя исключение не делать.

---

## 4. Запуск desktop

Обычный dev-запуск из корня проекта:

```sh
pnpm dev:desktop
```

Ожидание: Vite на `http://localhost:5173/`, Electron через `vite-plugin-electron`.
Не считать ошибкой, что скрипт в `apps/desktop` выглядит как обычный `vite`.

Production macOS:

```sh
pnpm build:desktop:mac
```

После сборки:

```sh
open -n apps/desktop/release/mac-arm64/Pyn.app
```

Важно:

- `apps/desktop/vite.config.ts` — намеренный обход с копированием
  `electron/preload.cjs` → `dist-electron/preload.cjs`. Не переводить preload в
  ESM и не убирать обход «для красоты» без ошибки и разрешения.
- Alias `bufferutil` / `utf-8-validate` связан с `ws` и Electron — не менять
  вслепую.
- Ошибка `cjsPreparseModuleExports`: сначала версии Node/pnpm/Electron и
  текущий `vite.config.ts`, потом минимальный фикс.
- «Красивое» решение (electron-vite, отдельная сборка main и т.п.) — только после
  typecheck + dev + production-сборки.

## 5. UI-изменения без серого экрана

Перед правкой UI — минимальный затронутый экран/компонент. Не менять глобальные
layout, providers, routing, preload, IPC, auth-flow без прямой необходимости.

После UI-правки:

```sh
pnpm --filter @pyn/desktop typecheck
pnpm dev:desktop
```

Минимальная ручная проверка:

- нет серого/пустого экрана;
- нет runtime error в консоли;
- виден login или рабочий экран;
- изменённый экран открывается;
- элементы не ломают размер окна.

Если серый экран:

1. не продолжать новые изменения;
2. первая runtime-ошибка в логе;
3. чинить только её;
4. снова проверить запуск.

---

## 6. Формат ответа

Коротко и по делу. В конце:

- что сделано;
- что получилось;
- нужны ли ещё действия: **да/нет**;
- если остановился — почему.

Не дублировать в ответе длинные логи, полные diff и содержимое файлов, если
пользователь об этом не просил.

---

## 7. Checkpoint и качество (не экономить в минус)

Экономия **не отменяет**:

1. Понимание цели и границ scope перед write.
2. Pre-change checkpoint (clean HEAD или stash с untracked) перед первой записью.
3. Минимальный coherent diff; не рефакторить соседнее.
4. Проверку: узкий typecheck/test + сценарий задачи; для UI — §5.
5. Честно писать, что **не** проверено.

Экономить на: лишнем чтении, болтовне, повторных сканах, декоративных отчётах.
**Не экономить на:** checkpoint, scope, evidence после изменения.
