# Регламент работы

Этот регламент - рабочее правило для любых ИИ-агентов в проекте Pyn. Он важнее
личных привычек агента, но не отменяет системные ограничения среды, безопасность
и прямые новые указания пользователя.

Главная цель: максимальная экономия токенов, команд и чтения файлов без потери
качества результата.

## 1. Старт задачи

1. Сначала кратко сформулировать реальную цель пользователя в 1-2 предложениях.
2. Дать короткий план на 3-6 пунктов.
3. Начинать действия только после плана.
4. Работать по одному проверяемому шагу за раз.
5. После каждого шага проверять результат.
6. Если направление не дало пользы, остановить его и не возвращаться без причины.

## 2. Экономия контекста

- Не читать файлы "на всякий случай".
- Не сканировать весь проект без точной причины.
- Не выводить большие логи целиком: использовать `tail`, `rg`, лимиты строк.
- Не повторять в ответе секреты, токены, cookie, ключи и большие payload.
- Не запускать дорогие сборки, если достаточно более дешевой проверки.
- Не делать несколько независимых расследований одновременно.
- Сначала проверять ближайшую гипотезу, потом расширять поиск.

Читать файлы, искать по проекту и запускать команды можно, если выполнено хотя бы
одно условие:

- без этого невозможно сделать следующий конкретный шаг;
- есть точная ошибка, которую нужно устранить;
- пользователь явно попросил проверить конкретное место;
- изменение затрагивает общий контракт, запуск, сборку или UI, и без проверки
  можно пропустить поломку.

## 3. Если регламент мешает

Если правило мешает нормально решить задачу, агент обязан остановиться и спросить
разрешение на исключение. Вопрос должен быть коротким:

- какое правило мешает;
- почему мешает;
- что именно агент хочет сделать;
- какой риск, если не сделать исключение.

Без явного разрешения пользователя исключение не делать.

## 4. Запуск desktop

Обычный запуск для разработки выполнять из корня проекта:

```sh
pnpm dev:desktop
```

Ожидаемое поведение: Vite поднимается на `http://localhost:5173/`, а Electron
стартует через `vite-plugin-electron`. Не считать ошибкой то, что скрипт в
`apps/desktop` выглядит как обычный `vite`.

Production-сборка macOS:

```sh
pnpm build:desktop:mac
```

После сборки можно открыть приложение:

```sh
open -n apps/desktop/release/mac-arm64/Pyn.app
```

Важно:

- `apps/desktop/vite.config.ts` содержит намеренный обход с копированием
  `electron/preload.cjs` в `dist-electron/preload.cjs`.
- Не переводить `preload.cjs` в ESM и не убирать этот обход "для красоты" без
  воспроизведенной ошибки и отдельного разрешения пользователя.
- Alias для `bufferutil` и `utf-8-validate` связан с `ws` и Electron-сборкой.
  Не менять его вслепую.
- Если есть ошибка `cjsPreparseModuleExports`, сначала проверить версию Node,
  pnpm, Electron и текущее состояние `vite.config.ts`, затем предложить самый
  малый фикс.
- "Красивое" решение допустимо только после проверки: обновление Node/Electron
  tooling, переход на `electron-vite` или отдельная сборка main-процесса должны
  сопровождаться typecheck, dev-запуском и production-сборкой.

## 5. UI-изменения без серого экрана

Перед правкой UI определить минимальный затронутый экран и компонент. Не менять
глобальные layout, providers, routing, preload, IPC и auth-flow без прямой
необходимости.

После UI-правки обязательно проверить:

```sh
pnpm --filter @pyn/desktop typecheck
pnpm dev:desktop
```

Минимальная ручная проверка:

- приложение открылось, нет серого/пустого экрана;
- консоль не показывает runtime error;
- экран логина или рабочий экран виден;
- измененный экран открывается;
- основные элементы не перекрываются и не ломают размер окна.

Если после правки появился серый экран:

1. не продолжать новые изменения;
2. найти первую runtime-ошибку в логе;
3. исправлять только ее;
4. заново проверить запуск.

## 6. Формат ответа

Отвечать коротко и по делу. В конце указывать:

- что сделано;
- что получилось;
- нужны ли еще действия: да/нет;
- если остановился - почему.
